# 青松（智能客服 Agent）· 关注问题深度解析

> 这份文档按 `关注.md` 的清单逐条展开，结合「智能客服 Agent」（青松方向）的真实工程语境作答。
> 全文围绕一条主线：**能交给程序的，不要交给模型**。
> 口径统一为：**分层 → 分流 → 闸门 → 兜底 → 可观测**。

---

## 0. 先说总原则：能交给程序的，不要交给模型

这句话落到工程上，要拆成五条可执行的规则，否则只是一句口号：

| 规则 | 含义 | 例子 |
|---|---|---|
| ① 能用规则判定的，不用模型 | 确定性逻辑必须有确定性实现 | 状态流转、金额计算、权限校验、字段格式 |
| ② 能用小模型的，不用大模型 | 分类、改写、抽取这类任务用小模型/微调模型 | 意图分类、槽位抽取、Query 改写 |
| ③ 能让模型选，不能让模型填 | 模型只输出**枚举/ID**，不输出自由文本参数 | 选工具、选动作，而不是拼参数 |
| ④ 模型输出必须可验证 | 每个模型产物都要有 Schema + 业务双重校验 | 不合法就重试或降级，绝不"先用了再说" |
| ⑤ 模型只能"建议"，不能"执行" | 写操作必须过策略网关 | 赔付、退款、改单走审批与限额 |

**判断一个环节该不该上模型的四问**：
1. 这个环节有没有唯一正确答案？→ 有，就写代码；
2. 错了以后能不能自动发现？→ 不能，就别让模型直接产出；
3. 错了以后代价大不大？→ 大，就必须加闸门或人工确认；
4. 有没有更便宜的可复现方案（规则/检索/小模型）？→ 有，优先用。

一句话收尾口径：**Agent 的价值在于"处理长尾和模糊"，而不是"替代确定性逻辑"。把确定性交还程序，模型才能把算力花在真正需要泛化的地方，系统也才可测、可审、可回滚。**

## 1. 架构是怎么样的

### 核心结论
分层架构 + **两级路由** + **模型与程序职责分离**。编排、判定、执行是程序的；理解、改写、生成是模型的；两者之间用 Schema 和策略网关隔开。

### 分层展开

```
① 接入层    多渠道会话接入、用户/租户识别、多轮会话上下文加载
② 编排层    意图识别 → 分级路由 → 状态机（多轮槽位补全）→ 调用编排
③ 能力层    RAG 检索、工具调用（MCP/注册中心）、业务工作流、摘要/改写
④ 执行层    策略网关（权限/限额/幂等/审批）→ 业务系统 API
⑤ 数据层    知识库（FAQ/政策/文档）、业务数据（订单/工单）、会话与审计日志
⑥ 治理层    评测集、灰度开关、埋点与看板、bad case 回流
```

各层的"模型含量"与降级策略（这张表是回答架构题的核心）：

| 层 | 组件 | 模型含量 | 降级策略 |
|---|---|---|---|
| 接入 | 会话网关、上下文加载 | 无 | 纯服务降级 |
| 编排 | 意图分类器 | 低（小模型） | 规则兜底 → 转人工 |
| 编排 | 多轮状态机 | 无 | 槽位缺失时澄清话术 |
| 能力 | Query 改写 | 低（小模型） | 原样检索 |
| 能力 | RAG 检索 | 中（向量 + BM25 + 重排） | 关键词检索兜底 |
| 能力 | 答案生成 | 高（大模型） | 模板话术 / 转人工 |
| 执行 | 策略网关 | 无 | 拒绝并告警 |
| 执行 | 业务 API | 无 | 重试 / 对账 |
| 治理 | 评测与看板 | 无 | —— |

### 三个必须讲清的设计决策

**① 为什么是两级路由（意图分类的关键）**
- 一级路由：轻量分类（规则 + 小模型/Embedding 相似度），10~50ms 出结果，覆盖绝大多数高频意图；
- 二级路由：只有置信度低于阈值时，才把候选意图 + 相关文档交给大模型复核（或用大模型做澄清问答）；
- 收益：**大部分流量不碰大模型**，成本、延迟、稳定性都可控；同时低置信度样本天然是**主动学习**的高价值样本。

**② 为什么要"主 Agent + 子 Agent/工作流"而不是一个大 Agent 自由发挥**
- 主 Agent 只负责：理解、路由、汇总；
- 每个意图域有独立的子流程（或子 Agent）：各自有专属提示词、专属工具集、专属验收标准；
- 好处：提示词更短更准、工具集更小（减少选错工具的概率）、单个域的改动不会污染其他域、可独立评测和灰度。

**③ 为什么一定要有策略网关**
- 模型输出 → 策略网关 → 业务系统，这个中间层是所有"防闯祸"能力的落点：权限校验、金额/次数限额、幂等键、审批流、灰度开关、审计留痕；
- 有了它，模型输出的最坏结果被限制在"建议被拒绝"，而不是"已经造成了资金损失"。

**④ 与"记忆/知识"的边界**
- 会变的事实（订单状态、工单进度）**永不进知识库**，一律实时查工具；
- 稳定知识（政策、话术、SOP）走 RAG；
- 会话上下文（本轮在聊什么）走记忆分层（见第 8 节）。

### 一句话收尾
**架构的本质是"确定性的骨架 + 概率性的肌肉"：骨架（路由、状态机、策略、审计）必须是可测可审的代码，肌肉（理解、生成）才用模型。**

## 2. 怎么做的意图分类

### 核心结论
把它当**路由问题**而不是**语义理解问题**：先定标签体系，再做多信号融合分级判定，低置信度才上升到大模型，**分类结果只做路由，绝不直接执行**。

### 展开回答

**（1）标签体系设计（先讲这个，体现工程成熟度）**
- 分层标签：一级=业务域（订单/物流/退款/发票/账号…），二级=动作类型（查询/办理/投诉/咨询），三级=可选的场景细分；
- 标签必须**互斥且完备**，并明确"多意图""闲聊""无法识别"三类的处理策略：多意图要拆解成串行子任务，闲聊走兜底，无法识别走澄清或转人工；
- 单独维护一个**风险/情绪标记维度**（和意图正交）：比如"投诉/威胁曝光/情绪激动"必须直接转人工，不能让模型硬答。

**（2）多信号融合分级判定**

| 级别 | 方法 | 特点 | 触发下一级的条件 |
|---|---|---|---|
| L1 | 规则/正则/关键词 + 实体命中 | 极快、精准，覆盖明确表达 | 未命中或多命中 |
| L2 | Embedding 相似度召回（对照意图样例库） | 快，能覆盖同义改写 | Top1 相似度 < 阈值 |
| L3 | 小模型分类器（BERT 类/微调小模型） | 准确率高、成本低、可批量 | 置信度 < 阈值 |
| L4 | 大模型 + 候选意图 + 相关文档 复核 | 泛化强、能处理复杂表达 | 仍低置信 → 澄清或转人工 |

关键点：**阈值不是一个，而是分档**（高置信直通 / 中置信走澄清 / 低置信转人工）；阈值用线上数据调，不拍脑袋。

**（3）分类结果的输出结构（结构化是后面一切校验的前提）**
```json
{
  "intent": "refund.query",
  "confidence": 0.87,
  "slots": { "order_id": "123456" },
  "risk": "low",
  "need_clarify": false,
  "route": "sub_agent_refund"
}
```
注意 `route` 是**枚举**，不是自由文本——这就是"能让模型选，不能让模型填"。

**（4）数据与训练（讲清楚怎么从 0 建起来，这是加分点）**
- 冷启动：业务梳理人头意图 → 生成式标注 + 人工审核（LLM 只做初筛，人来定稿）；
- 扩量：线上日志伪标注 + **主动学习**（优先标注低置信度、高分歧、被改道的样本）；
- 难例建设：多意图、改主意（"算了，我是想问…"）、口语化、错别字、指代（"它还没到"）；
- 每个标签保留一份**Golden Set**，任何模型/prompt 变更都要跑回归。

**（5）怎么衡量好坏（指标要分业务和模型两层）**
- 模型层：Top-1 准确率、**混淆矩阵**（重点看危险混淆，比如"查询"被判成"退款"）、低置信兜底率；
- 业务层：**路由准确率**（真正决定体验）、澄清率、转人工率、误路由导致的二次转接率；
- 一个重要的经验：**意图分类的准确率不等于业务成功率**，所以要直接在业务漏斗上看指标，而不是只盯着分类 F1。

**（6）最需要避免的错误**
- 让分类器直接触发写操作（必须经过下游的状态校验和策略网关）；
- 把意图分类当成一次性工作（业务会新增意图，需要持续维护机制，比如新意图发现的聚类巡检）；
- 用大模型做全量分类（成本和延迟不可接受，且没必要）；
- 忽略"多意图"和"改主意"（客服场景里这类占比很高，处理不好体验断崖式下降）。

## 3. 怎么保证模型生成、执行的正确性

### 核心结论
把模型当**不可信组件**来对待：**四道闸门**——出参约束（Schema）→ 语义校验（真实性/域内性）→ 策略网关（权限/限额/幂等/审批）→ 事后校验与回滚。执行侧的核心是"模型只建议、程序才执行"。

### 展开回答

**（1）生成侧的四道闸门**

| 闸门 | 做什么 | 失败处理 |
|---|---|---|
| ① 出参约束 | 强结构化输出（Function Calling / JSON Schema / 枚举白名单） | 重试（有限次）→ 降级模板 → 转人工 |
| ② 语义校验 | ID 真实性、参数域内性、金额/时间合理性、动作白名单 | 拒绝执行，返回可解释原因 |
| ③ 策略网关 | 权限、限额、幂等键、审批流、灰度开关 | 拦截并告警 |
| ④ 事后校验 | 执行结果与预期比对、状态回读、异常回滚 | 补偿/回滚 + 告警 |

**（2）真相约束：不允许模型"凭记忆回答"**
- 事实类回答必须走 **RAG 且带引用**，生成内容要能被原文支撑（faithfulness 校验）；
- 检索不到或证据不足时，**必须拒答/转人工**，而不是让模型"合理推测"；
- 关键字段（金额、时效、政策条款）用**结构化抽取 + 程序拼装**，不让模型自由生成数字。

**（3）执行侧的三条铁律**
- **幂等**：所有写操作带幂等键（业务 + 参数确定性生成），保证重试安全；
- **状态回读**：写之前查当前状态（乐观并发），避免覆盖别人的修改；写之后回读校验；
- **可逆优先**：能设计成"设置目标状态"就不设计成"增量修改"；不可逆动作（赔付）一律加人工审批 + 限额。

**（4）为什么"能交给程序的不要交给模型"在这里最关键**
- 金额计算、时效推算、库存判断、优惠叠加这些**有唯一正确答案**的逻辑必须用代码；
- 模型做的是：把用户的话翻译成结构化请求、把程序结果翻译成人话；
- 这样"正确性"就变成了**可测试的代码问题**，而不是"抽检模型输出"。

**（5）工程上的兜底习惯**
- 每个模型调用都有超时、重试、降级路径；
- 每一次模型产物（输入、输出、校验结果）都留痕，用于复盘和回归集补充；
- 关键指标做**双写校验**：新链路结果与老链路/规则结果做影子比对，差异超阈值就暂停放量。

### 追问：如果是查询数据，怎么保证查询数据的准确性

**核心结论**：**不让模型写查询**。指标口径唯一定义、查询模板化、参数从槽位来、权限在数据层兜、结果做一致性校验。

- **口径唯一（第一优先级）**：一个指标只能有一个定义（数据源、时间口径、时区、是否含退款、是否含测试单…），沉淀在**指标字典/语义层**里；模型只能引用指标名，不能自己定义口径。多数"数据不准"的投诉，根因是口径不唯一而不是模型算错。
- **查询模板化 + 参数化**：把常用查询固化成模板（如"按订单号查物流""按时间段查消耗"），模型只负责**填槽**（order_id、时间范围），绝不直接生成 SQL；如必须开放查询能力，则限定在受限 DSL/只读视图 + 强制 LIMIT + 字段白名单 + 禁止跨租户。
- **参数校验**：ID 必须真实存在且属于当前用户（防幻觉 id + 防越权）；时间范围限幅（比如最多查 90 天）；金额/百分位做域内校验。
- **数据层兜底**：只读账号、行级权限（RLS）、租户隔离；查询在数据层做过滤而不是在应用层做，避免越权取数。
- **一致性校验**：关键数字做二次校验——跨表交叉核对、与实时口径比对、异常值检测（比如消耗比历史均值高 10 倍就标记为可疑而不是直接展示）；结果里带上"数据截止时间"，避免用户误读。
- **缓存与实时性的取舍**：汇总类走离线表（快且稳），明细类走实时接口（准但慢）；两者不一致时明示口径和更新时间，而不是混着用。
- **渲染层**：数字由程序格式化（单位、千分位、币种），避免模型把 `10000` 说成 `1万` 或算错百分比。

## 4. 模型幻觉怎么解决的

### 核心结论
幻觉分三类，**对症下药**：知识型靠"检索 + 引用 + 拒答"，工具型靠"结构化 + 真实性校验"，表达型靠"模板化 + 后置校验"。核心思路是**不给模型编造的机会**，而不是事后检查它有没有编。

### 展开回答

**（1）先分类，再施策**

| 幻觉类型 | 表现 | 治理手段 |
|---|---|---|
| 知识幻觉 | 编造政策、时效、条款 | 强制 RAG + 引用溯源 + 证据不足则拒答；答案与原文做一致性校验 |
| 工具/参数幻觉 | 编造订单号、计划 id、接口参数 | Function Calling 强约束 + ID 真实性校验（必须回查）+ 枚举白名单 |
| 计算/数值幻觉 | 算错金额、比例、日期 | 数值一律由程序计算；模型只做表述；禁让模型做算术 |
| 表达幻觉 | 过度承诺、语气不当、泄露信息 | 输出侧模板/敏感词/合规校验；高风险场景固定话术 |
| 越权幻觉 | 声称"已为您办理"（实际没做） | **状态以系统回读为准**，措辞由程序按真实状态生成 |

**（2）六个具体手段（按性价比排序）**
1. **检索前置 + 引用强制**：先给证据再让模型说结论；没有证据就不许下结论；
2. **拒答与转人工是一等公民**：把"我不知道，帮您转人工"设计成正常路径，而不是异常路径——这是最有效的防幻觉手段；
3. **结构化输出**：模型输出枚举/ID/Schema，自由文本只用于最后的话术包装；
4. **数值与状态由程序产出**：模型只负责"怎么说"，不负责"是什么"；
5. **后置校验（critic/verify）**：小模型或规则做一致性检查（引用是否支撑结论、数字是否与工具结果一致、有没有"已办理"这类承诺词），不通过就重生成或降级模板；
6. **提示词与上下文卫生**：明确角色边界与拒答规则、Few-shot 只给正例与边界例、把外部内容（用户输入、检索片段）标记为"数据"而非"指令"，降低注入诱导。

**（3）为什么"能交给程序的，不要交给模型"是治本**
- 幻觉的根源是模型在**没有事实来源**的地方做生成；
- 把事实、数值、状态全部从模型手里拿走，模型剩下的任务就只是"把已知事实说清楚"，幻觉空间被压缩到最小；
- 这也是可评测的前提：事实由程序产出之后，"正确性"变成可断言的东西。

## 5. 沙箱问题

### 核心结论
沙箱不是只有"跑代码"才需要。Agent 场景的沙箱是**四层隔离**：执行隔离、资源隔离、权限隔离、数据隔离。**默认不可信，约束在外部强制。**

### 展开回答

**（1）什么时候需要执行沙箱**
- 让模型生成/执行代码（数据分析、脚本任务）；
- 解析不可信输入（用户上传的文件、网页、正则、模板）。

约束清单：
- **进程/容器隔离**：独立容器或受限执行环境，跑完即销毁；不共享宿主文件系统与网络；
- **资源限额**：墙钟超时、CPU 时间、内存上限、进程/线程数、打开文件数、输出字节上限；
- **网络**：默认不出网；需要时走白名单代理；
- **文件系统**：只挂载必要目录（临时目录只写），只读挂载代码与数据；
- **终止**：跑在独立进程组 / Job Object 里，**级联杀干净**，避免孤儿进程；
- **禁交互**：检测到读 stdin 直接判失败，绝不阻塞等待；
- **版本冻结**：只允许执行注册过、带版本的脚本，禁止临场生成任意代码直接执行（要生成则走静态检查 + 沙箱 + 审核队列）。

**（2）工具权限沙箱（客服场景更常用）**
- 工具按风险分级：`只读` / `低危写` / `高危写`；
- 只读工具可直接调用；低危写加限额 + 幂等；**高危写（赔付、退款、改价）必须审批或双人复核**；
- 每个工具有独立凭证，**最小权限**，且按当前用户身份鉴权（而不是用超级账号代跑，否则等于绕过业务权限）；
- 敏感工具默认关闭，靠**灰度开关**按租户/场景逐步放开。

**（3）数据沙箱（最容易被忽略，但客服场景最关键）**
- **租户隔离**：检索与查询必须带租户/主体过滤，且在数据层强制（RLS），不能靠 prompt 约束；
- **知识库权限**：不同业务线/角色可见的知识范围不同，检索时就过滤，避免"检索到不该看的内容再靠提示词别输出"这种伪安全；
- **敏感信息**：手机号、地址、身份证等在进入模型上下文前**脱敏或做 token 化替换**，模型只处理占位符，出口再还原；
- 会话与模型输入输出**留痕可审计**，但存储侧加密 + 访问受控。

**（4）Prompt 注入沙箱（Agent 特有）**
- **输入不可信原则**：用户输入、工具返回值、检索到的文档、网页内容，一律视为**数据**，不作为指令；
- 用结构化边界明确区分"系统指令"与"外部数据"（分隔符 + 明确声明 + 不把外部文本拼进指令区）；
- **工具返回值也可能是攻击面**（间接注入），高风险工具返回的内容不直接进模型决策链，先做抽取和校验；
- 能力降级：即便注入成功，攻击者能拿到的也只是"一个受限工具的调用权"，因为**真正的权限在策略网关和数据层**。

**（5）一句话收尾**
**沙箱的边界应该画在"能力的授予"上，而不是"提示词的约束"上。** Prompt 层的限制是软约束，工程层的限额、鉴权、审批才是硬约束。

## 6. 怎么解决超时问题

### 核心结论
超时不是"异常"，是**必须设计的正常状态**。分三层设预算（模型层 / 工具层 / 链路层），每层都要有**确定返回值 + 降级路径**，且**区分"未发出"和"结果未知"**。

### 展开回答

**（1）模型调用层**
- 独立设**首 token 超时**（挂起最常见的地方）与**整体超时**；流式场景用心跳/空闲超时判定"卡住"；
- 超时重试策略：首 token 前挂起可安全重试（带退避 + 抖动）；已开始流式输出则谨慎（可能有部分内容已产生）；
- 降级阶梯：换更小模型 / 换备用端点 / 简化 prompt（压缩上下文）/ 直接走模板话术；
- 体验优先：**能先吐的部分先吐**（流式），把等待转化为可感知的进度，而不是干等。

**（2）工具调用层**
- 分层超时：连接超时 < 读超时 < 工具总超时 < 单步看门狗；
- 长任务**异步化**：提交任务拿 handle，之后轮询或等回调，绝不阻塞地等；
- 超时必须**取消底层请求**（AbortSignal / CancellationToken 传到底层 HTTP、DB、子进程），否则线程和连接会泄漏；
- 熔断：同一工具连续超时 N 次进入隔离名单，向编排层报告"该工具暂不可用"，让流程换路径或降级；
- **结果未知的处理**（客服场景的写操作尤其重要）：写超时不等于失败，进"待核对队列"，靠幂等键查询真实状态，而不是盲目重试。

**（3）链路层（面向用户体验的兜底）**
- 总时长预算（比如 8 秒）：超了就先回"正在为您查询，稍后同步结果"，把同步等待转成异步通知 / 工单 / 转人工；
- 每个意图预设**最大轮次和最大工具调用数**，防止多轮检索+工具的组合把总时长拖爆；
- 快速失败优先于慢速成功：宁可提前转人工，也不让用户对着"正在输入"等 30 秒。

**（4）兜底与对账（防"卡死"）**
- Agent 主循环必须能推进：超时后重试（有限次）→ 换工具 → 跳过并如实告知 → 转人工；**任何路径都不能原地等待**；
- 所有"发出但无响应"的写操作落到对账队列，由定时任务收敛；
- 进程隔离保证单个工具卡死不影响主流程（详见沙箱一节）。

## 7. 开源上下文压缩解决方案

### 核心结论
开源方案可以借鉴**机制**，但落地要**自研组装层**。业界主流思路是三类：滑动窗口、摘要/滚动压缩、分层记忆 + 检索。真正的难点不在"怎么压"，而在"**在哪里压、压完怎么保证不丢关键状态**"。

### 展开回答

**（1）值得借鉴的机制（按思路归纳，不依赖具体库）**
- **滚动摘要（rolling summary）**：保留最近 N 轮原文，更早的内容由模型持续增量摘要维护成一份"会话状态"；代表思路来自长期记忆类架构（如 MemGPT 的分层记忆管理、以及"对话摘要缓冲"类模式）；
- **滑动窗口 + 关键信息锚定**：丢弃旧轮次，但把关键实体（订单号、金额、用户诉求）抽出来常驻，避免丢；
- **分层记忆 + 检索**：把历史写入外部存储（向量库/文档），需要时按需召回，而不是常驻上下文；
- **结构化状态卡**：把对话压成"已确认事实 / 已尝试方案 / 待办 / 用户情绪"四段式，比自由摘要稳定得多；
- **框架内置的上下文管理**：主流 Agent 框架（LangChain/LlamaIndex/AutoGen 等）都提供 Memory / summary buffer / trim 类组件，可以直接复用其**接口抽象**（把它们当"压缩策略插件"），但要注意它们普遍只解决"压缩"，不解决"协议边界和缓存命中"。

**（2）为什么不建议直接用开源方案做主线**
| 问题 | 说明 |
|---|---|
| 协议安全 | 通用库常常按 message 粒度裁剪，容易切坏 `tool_calls`/`tool_result` 的配对，导致请求被拒 |
| 缓存友好性 | 改写靠前内容会让 Prompt Cache 全失效，成本与首字延迟骤升，通用库一般不关注 |
| 业务关键信息 | 通用摘要器不知道"订单号/金额/用户硬约束"不能丢，会当普通文本一起压掉 |
| 多租户合规 | 摘要里可能残留敏感信息，需要脱敏和权限过滤，开源实现不含这层 |
| 可观测性 | 缺少"压缩前后 token、丢失字段、可追溯引用"的埋点，出问题无法复盘 |

**（3）我倾向的落地方案（自研组装层 + 可插拔策略）**
- 存储层：**完整会话只追加、永不改写**（审计与回溯的唯一真相源）；
- 组装层：每次调用前生成"投影视图" = 固定头（角色/业务规则/工具定义） + 压缩后的中段 + 最近 K 轮原文 + 当前未完成的工具链；
- 压缩策略做成**可插拔插件**，按破坏性递增依次尝试：外置引用 → 只回执 → 结构化摘要 → 滑窗 → 重开会话；
- 安全边界：**压缩点只落在完整 step 之间**，工具调用与其结果视为原子块；
- 关键状态白名单：订单号、金额、已确认事实、用户硬约束、未解决错误必须进入状态卡，且**压完做校验**（关键字段是否还在）；
- 指标化：压缩次数、节省 token、缓存命中率、压缩后任务成功率（用来验证压缩没有伤害效果）。

**（4）一句话收尾**
**压缩的本质是"视图"而不是"记录"：记录永远完整，视图按预算动态生成。开源方案给的是策略，边界、白名单、缓存和可观测性必须自己做。**

## 8. 记忆、知识库分层

### 核心结论
**记忆是"关于这次/这个人的"，知识库是"关于业务的"，两者绝不能混。** 记忆按生命周期分层（工作记忆 / 会话记忆 / 长期记忆），知识库按用途分层（政策文档 / FAQ / 业务数据）。

### 展开回答

**（1）记忆分层（按生命周期）**

| 层 | 内容 | 存储 | 生命周期 | 用法 |
|---|---|---|---|---|
| 工作记忆 | 当前轮消息、当前工具调用与结果 | 内存/上下文 | 单轮 | 直接进上下文 |
| 会话记忆 | 本次会话的摘要状态卡、已确认槽位 | KV + 会话库 | 会话级 | 每轮加载，压缩维护 |
| 长期记忆 | 用户画像（等级、偏好、历史工单）、历史会话要点 | 关系库 + 向量库 | 长期 | **按需检索注入**，不常驻 |
| 业务事实 | 订单状态、工单进度、账户余额 | **不缓存**，实时查 | 实时 | 走工具，永不进知识库 |

三条纪律：
- **会变的事实不进记忆库**（否则"记忆"会变成"错误信息的永久来源"）；
- 长期记忆要**可解释、可删除**（用户问"你怎么知道的"要能说出出处；合规上要能删除）；
- 记忆写回要**受控**：只写结构化、可校验的信息（用户明确说的偏好），不让模型自由写"总结性记忆"，否则错误会被固化并持续放大。

**（2）知识库分层（按用途）**

| 层 | 内容 | 检索方式 | 关键要求 |
|---|---|---|---|
| 政策/规则文档 | 退款政策、时效、SOP | 分块 + 混合检索 + 重排 | 版本与时效标注（**过期文档是客服最大的幻觉源**） |
| FAQ/标准问答 | 高频问题标准答案 | 相似度直出，高阈值 | 命中原样输出，不让模型改写关键信息 |
| 业务数据 | 订单、物流、工单 | **工具调用**，不是检索 | 实时性、权限、准确性 |
| 话术库 | 安抚、催办、结束语 | 模板匹配 | 高风险场景强制使用固定话术 |

**（3）检索策略（决定效果的关键在检索，不在生成）**
- **混合检索**：向量（语义）+ BM25/关键词（专有名词、编号），再加重排模型精排；
- **元数据过滤**：业务线、生效时间、文档版本、租户/角色权限——**过滤要在检索阶段做**，不能检索出来再靠提示词"别看"；
- **分块策略**：按语义结构分块（标题/条款级），带上下文标题拼接，避免把一条政策切成两半；
- **召回不足的处理**：改写 Query 重试一次 → 关键词兜底 → 仍不行就澄清或转人工（**不许硬答**）；
- **可溯源**：每个回答带文档来源与版本，既支撑校验也支撑复盘。

**（4）两者交界处的两个典型设计**
- **会话内的"事实"**：用户说"我要退的是上周那单"→ 抽取成结构化槽位（订单号）存会话记忆，后续每轮复用，而不是每轮重新问；
- **长期记忆的注入时机**：只在需要个性化时检索（比如"按我的地址"），并且注入时**标注来源和时效**，避免把半年前的偏好当现状用。

**（5）一句话收尾**
**知识库解决"业务怎么说"，记忆解决"这个人是什么情况"，工具解决"现在事实是什么"。三者混淆就会出现"用过期政策回答 + 用旧偏好推断 + 用记忆里的旧订单号操作"这三类典型事故。**

## 9. 评测怎么做的

### 核心结论
分**离线评测（回归）与在线评测（业务指标）两层**，并且要有**漏斗式的过程指标**定位问题发生在哪一环。核心原则：**业务指标优先于模型指标**，评测集要能随 bad case 持续生长。

### 展开回答

**（1）离线评测（发版前的守门人）**

| 环节 | 指标 | 说明 |
|---|---|---|
| 意图分类 | Top-1 准确率、混淆矩阵、危险混淆率 | 重点盯"查询↔退款"这类高危混淆 |
| 检索 | recall@k、MRR、命中率 | 召回不够时先别动生成，先修检索 |
| 生成 | 忠实度（faithfulness）、答案正确率、引用准确率 | 事实类必须能校验是否被原文支撑 |
| 端到端 | 任务成功率、完成轮次、工具调用正确率 | 用**黄金集**跑全链路 |
| 安全/合规 | 越权拦截率、敏感信息泄漏率、拒答正确率 | 这类指标要求是"零容忍" |

评测集三层结构：
- **核心回归集**：稳定、有标准答案、每次发版必跑（防止"改 A 坏 B"）；
- **边界/难例集**：多意图、改主意、口语化、错别字、长尾意图、情绪激动；
- **对抗集**：注入、诱导越权、套取他人信息、要求承诺赔付。

方法上：**LLM-as-judge + 人工抽检双轨**——用模型评分做大规模回归（要固定 judge 版本、用 rubric 打分、定期与人工校准一致性），关键场景和争议样本由人工定稿。

**（2）在线评测（决定要不要放量）**

| 类别 | 指标 |
|---|---|
| 业务结果 | 解决率 / 一次解决率、转人工率、二次转接率、满意度（CSAT）、工单量变化 |
| 过程漏斗 | 意图分类置信度分布、澄清率、检索命中率、RAG 拒答率、工具成功率、超时率 |
| 成本效率 | 单会话 token 成本、模型耗时 P50/P95、单问题模型调用次数 |
| 风险 | 误操作数、拦截数、投诉/升级数、回滚次数 |

**（3）放量机制（把评测和发布绑起来）**
- **影子流量**：新链路只跑不生效，产出差异报告，观察与人工/旧链路的偏差；
- **A/B 实验**：随机分流，观察业务指标（不是模型指标）；注意客服场景要按会话/用户分流，避免同一用户跨组；
- **灰度**：按租户/意图/流量比例逐步放量，每步设**止损阈值**（比如解决率下降超 X% 或误操作超 N 次自动回滚）；
- **bad case 回流闭环**：线上差评、转人工、被改道的会话定期抽样聚类 → 标注 → 进评测集 → 修 prompt/检索/代码 → 回归。

**（4）三个经验性的坑**
- **只看模型指标会误判**：生成指标涨了但转人工率没降，说明"答得更好但没解决用户问题"；
- **评测集静态化会失真**：业务和政策会变，评测集必须季度更新，并给政策类知识做版本标注；
- **同一套 prompt 打天下**：不同意图域应该分开评测、分开调优，合在一起的平均指标会掩盖某个域的严重退化。

**（5）一句话收尾**
**离线评测保证"不发版退步"，在线评测保证"确实有用"，bad case 回流保证"持续变好"。三者缺一，评测就会变成走过场。**

## 附：全场收尾口径

如果面试官问"你从这个项目里最大的收获是什么"，可以这样收：

> 客服 Agent 的核心矛盾是——**用户要的是"确定的结果"，而模型给的是"概率的表述"**。
> 所以工程上的解法是三层：**把确定性还给程序**（规则、状态机、数值计算、口径统一）、**把不确定性框在闸门里**（Schema 校验、真实性校验、策略网关、审批与限额）、**把过程变成可观测可回归的**（漏斗指标、黄金集、影子流量、bad case 回流）。
> 我的一条基本判断是：**能交给程序的，不要交给模型；必须交给模型的，一定要有可验证的兜底。**
