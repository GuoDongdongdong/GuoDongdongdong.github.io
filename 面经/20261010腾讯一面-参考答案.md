# 一、八股部分

## 1. Agent 上下文怎么管理

**【核心结论】**
把上下文当成一种**稀缺的预算资源**来管理，核心是四件事：**分层装载、预算分配、分级压缩、外置引用**。上下文里只保留"决策和状态"，原始数据一律外置。

**【展开回答】**

（1）先把上下文分层，不同层的生命周期和压缩策略不同：

| 层 | 内容 | 压缩策略 |
|---|---|---|
| 系统层 | System Prompt、工具 Schema、Few-shot、输出格式约束 | 基本不动，追求稳定以命中 Prompt Cache |
| 任务层 | 当前目标、计划/Todo、约束条件、验收标准 | 结构化维护，变更时**整体替换**而非追加 |
| 工作层 | 最近 N 轮对话、最近工具调用与结果 | 原样保留（这是模型推理的直接依据） |
| 长期层 | 历史摘要、产物引用（artifact 路径）、检索到的记忆 | 按需检索注入，不常驻 |

（2）预算分配：`可用预算 = 上下文窗口 − max_output_tokens − 安全余量`。按层设定配额（例如工作层不超过 50%），并记录每次调用的 `prompt_tokens` 实际值——**用真实计费 token 而不是字符估算**来驱动压缩决策。

（3）分级压缩：按"破坏性从小到大"排序，优先用便宜手段。
- L0：超长工具结果截断 + 落盘引用；
- L1：工具结果只回执（状态码 + 关键字段 + 条数），明细走 artifact；
- L2：话题级摘要，把一段多轮对话压成一段结论；
- L3：滑动窗口丢弃最旧的完整轮次；
- L4：换更小/更长上下文的模型，或开新会话并继承摘要。

（4）外置引用（最关键的一条设计原则）：
- 大结果不塞进上下文，而是存成 artifact，上下文里只留 `{path/id, 摘要, 如何按需取回}`；
- 长文档走检索，按需召回相关片段；
- 需要全量处理数据时，**用子 Agent（Sub-agent）在独立上下文里处理，只把结论回传主 Agent**。

（5）要避免的反模式：回放全部工具结果、把整个文件内容贴进对话、用"总结一下"处理一切（昂贵且丢信息）、每次都重写 System Prompt 导致缓存全失效。

一句话收尾：**上下文的容量是成本、延迟和准确率三个指标的交汇点，管理动作的本质是在"保真度"和"预算"之间做显式取舍，而不是等溢出了再抢救。**

**【追问预判】**
- "为什么强调分层？" → 因为不同层的信息稳定性不同，稳定层不动可以吃 Prompt Cache，动态层才是压缩对象。
- "你怎么知道上下文快满了？" → 见下一题（水位线 + 真实 token 计数 + 预判增长）。

## 2. 什么时候触发上下文压缩

**【核心结论】**
压缩的触发点是 **LLM 调用前的组装阶段**，判断依据是**水位线（可用预算占比）+ 增长预判**，而不是"等报错再压"。

**【展开回答】**

（1）四个明确触发时机：

| 时机 | 说明 |
|---|---|
| 每次调用模型前 | 组装 prompt 时检查 `已用 token / 可用预算`，超过高水位（如 75%）先压后调 |
| 追加新用户消息前 | 用户消息 + 预期回复可能挤掉尾部关键信息，提前腾空间 |
| 工具结果入上下文前 | **最关键的兜底点**：单个工具结果可能一次就撑爆，必须在写入上下文前预处理 |
| 主动规划式压缩 | 任务切换、里程碑完成、长任务分段推进时，主动把已完成阶段压缩归档 |

（2）判断依据：
- 主依据：`prompt_tokens + 预计下一轮 output` 与可用预算的比值，触达高水位线（低水位不压，避免频繁扰动）；
- 辅助依据：**增长速率**——如果单轮增长很快（比如工具结果动辄几万 token），要把水位线调低，提前压；
- 语义依据：出现"模型开始重复之前已做的事""引用不上前文""反复问已经给过的信息"这类信号，说明有效上下文已经在退化，需要压缩而不是继续追加；
- 成本依据：压缩会打断 Prompt Cache，所以要在"该压"和"别压太勤"之间取一个阈值区间（例如 60% 预警、75% 压缩、90% 强制）。

（3）核心原则：**压缩要在"有余量"的时候做，不要等到"没余量"才做**。因为强制压缩时没有选择空间的余地，只能丢信息，风险最高；主动压缩时还能选择保留什么、丢弃什么。

**【追问预判】**
- "阈值定多少合适？" → 不是一个固定数字，取决于工具结果的平均大小和任务长度；先测出典型的单轮增长率，再让高水位 = 100% − 2~3 轮最大增长量。
- "压缩会不会太频繁导致抖动？" → 设双阈值滞回（超过 75% 压到 50% 以下），避免每轮都触发。

## 3. 上下文怎么压缩，判断依据是什么

**【核心结论】**
按**"破坏性递增"的顺序多级压缩**，判断依据是**信息在后续推理中还会不会被用到**——会被用到的留结论，不会被用到的不留。

**【展开回答】**

（1）压缩手段分级（从便宜到贵，能用低级就不用高级）：

| 级别 | 手段 | 适用对象 | 代价 |
|---|---|---|---|
| L0 | 截断 + 落盘引用 | 超长工具输出、日志、大 JSON | 近似零成本 |
| L1 | 只回执摘要 | 工具调用结果 | 零成本，但可能丢细节 |
| L2 | 结构化摘要 | 一段已结束的多轮对话 | 一次额外 LLM 调用 |
| L3 | 滑动窗口丢弃 | 最旧的完整轮次 | 有信息损失 |
| L4 | 重开会话 / 换模型 | 整体膨胀 | 有上下文断裂风险 |

（2）不同内容的压法不一样，不能一刀切：
- **工具结果**：优先**离场外置**——全量写入 artifact，上下文只留 `{status, 关键字段, 条数, 引用 id, 取回方式}`；确实要截断时只截尾部并**显式标注已截断**，绝不悄悄截中间；
- **长文档/网页**：分块 + 检索，按需注入相关片段，不整篇进上下文；
- **对话历史**：用固定模板产出**状态卡**——已完成、当前进展、待办、硬约束、关键 ID、未解决错误。用模板约束而不是自由发挥，保证每次压缩产出结构一致、信息不丢；
- **图片/多模态**：转成文字描述或关键属性，原始图留引用；
- **重复内容**：检索替代复制。

（3）判断依据（逐条问四个问题）：
1. 这条信息后续步骤还会被引用吗？→ 不会，直接丢；
2. 它是**过程**还是**结论**？→ 过程丢，结论留；
3. 它是**可再取的**还是**一次性的**？→ 可再取的外置，一次性的必须留摘要；
4. 丢了之后能不能**被检测到**并恢复？→ 能检测才敢丢，信息丢失要有损毁标记。

（4）必须钉死保留的东西：用户的硬约束与偏好、关键实体 ID、未解决的错误与异常、已经做出的决策及理由、当前待办。这几类是"丢了就一定出错"的信息。

（5）底线：**压缩必须可追溯**。摘要里保留来源指针，需要时可以回到原始记录，而不是让信息凭空消失。

## 4. 怎么选取压缩点位

**【核心结论】**
压缩点必须选在**不破坏对话因果结构的安全边界**上，最小压缩单位是"一个完整的助手 step（含其全部工具调用与结果）"，而不是单条 message。

**【展开回答】**

（1）硬约束（协议层，先讲这个，面试官最认）：
- `assistant(tool_calls)` 与紧随其后的 `tool` 结果**是一个原子块**，中间不能插任何东西，也不能只保留一半；
- user 消息与其首轮 assistant 回复不能拆开；
- 因此**压缩单位 = 一个完整 step**，压缩点只能落在两个 step 之间。

（2）三段式布局定位压缩点：

```
[固定头]  System Prompt + 工具定义 + 硬约束          ← 永不压缩
[可压中段] 较早期的历史 step（含已结束的子任务）      ← 压缩区
[固定尾]  最近 K 轮 + 当前未完成的工具调用链         ← 永不压缩
```

中段的起止就是压缩点：起点取"第一个非边界 step 之后"，终点取"最近 K 轮的边界之前"。两头都要按 step 边界对齐，再根据 token 预算微调边界位置。

（3）选取时的取舍原则：
- **就近保留**：越近的历史越相关，尾部保留 K 轮（K 按任务类型定，比如 3~6 轮）；
- **未完成不压**：进行中的工具调用链、还没被消费的结果，一律不压；
- **异常不压**：报错信息和异常上下文靠近当前决策的，保留原文，压缩会丢关键细节；
- **决策留、过程丢**：只压掉中间的探索过程，保留每个子任务的结论；
- **避免切在"推理链中间"**：如果某几步是连续推理（比如先查 A 再根据 A 查 B），要整段保留或整段压缩，不能从中间切断。

（4）工程实现上，压缩点用一个"step 边界索引 + 预算游标"来计算：从尾部往前累加 token，累到预算上限的那个 step 边界，就是压缩终点；再往前找到保留区起点，中间部分交给压缩器。

（5）一个重要提醒：**压完要校验**。压缩后重新检查是否满足所有协议约束（工具调用配对完整、角色序列合法），不合法就回退到上一级压缩手段（比如少压一点、换成 L0 截断）。

## 5. 压缩时机可以在用户和模型对话中间吗，如果不能的话为什么

**【核心结论】**
**不能"在中间插入"压缩动作**。压缩是一个**视图层操作**，只能在安全的 step 边界上、在模型调用之前做；对话本身是**只追加（append-only）**的。

**【展开回答】**

（1）三条硬约束：

**① 协议约束（最直接的理由）**
OpenAI / Anthropic 等接口要求 `assistant(tool_calls)` 后面必须紧跟对应的全部 `tool` 结果，中间不能插入 user 消息或其他内容，否则请求直接被拒（400）。在用户与模型交互中途插入压缩产物，很容易破坏这个配对关系。

**② 前缀缓存约束（性能与成本）**
对话历史和 KV Cache 都是**前缀式**的：改动越靠前的内容，后面全部缓存失效，成本和首字延迟会明显跳升。插在中间等于把整个前缀作废，属于最坏的一种改法。

**③ 语义约束**
中途插入一段"这是之前对话的摘要"会让模型无法确定这段内容属于谁、什么时候产生的，容易引发角色混淆和幻觉（比如把摘要内容当成用户的新指令）。压缩产物放在开头/边界处，语义最清晰。

（2）正确做法——**把压缩实现成"视图"而不是"记录"**：
- 原始对话在存储层**完整保留、只追加、永不改写**，这是审计和回溯的依据；
- 每次调用模型时，由"上下文组装器"生成一个**投影视图**：`固定头 + 压缩后的中段 + 最近 K 轮原文`；
- 于是"压缩"只发生在**组装阶段**，对存储层是只读的，不需要在对话中间插入任何东西；
- 好处：压缩错了可以重来（原始数据还在）、可以换不同压缩策略做 A/B、可以对同一条历史生成不同视图喂给不同模型。

（3）唯一允许的"位置"：**在两次模型调用之间、在追加下一条消息之前**。也就是"轮的边界"，而不是"轮内"。

一句话收尾：**对话记录和上下文视图要解耦。压缩作用于视图，不作用于记录，位置自然就只能落在轮边界上。**

## 6. 模型调用工具返回 token 超过上下文限制怎么办

**【核心结论】**
**绝不能"截断后硬塞"**。原则是：**入上下文前先做预算检查，超限则外置 + 摘要 + 引用**；需要全量处理时用子 Agent 隔离处理。

**【展开回答】**

（1）第一道闸门放在**工具层/结果处理层**，而不是等模型报错：
- 工具调用返回后，先估算 token，超过单条上限就走**预处理管道**，绝不直接写入上下文；
- 预处理结果形态：`{状态, 关键字段, 条数/统计量, 摘要, 全量数据引用(id/path), 取回方式}`。

（2）具体手段（按优先级）：
1. **落盘引用**：全量结果存成 artifact，上下文只留引用 + 简短摘要；
2. **分页/流式 + 按需取回**：告诉模型"结果共 N 条，已展示前 M 条，可按区间/过滤条件继续取"，让模型自己决定要不要更多；
3. **子 Agent 隔离处理**：需要全量数据时，起一个独立上下文的子 Agent 去读、算、筛，**只把结论回传**——这是唯一能"真正处理超大数据"又不炸主上下文的办法；
4. **工具侧改造**：要求工具本身支持分页、过滤、聚合下推，**返回聚合值而不是明细**（比如直接返回 count/sum 而不是一万行原始记录）；
5. **截断的最后手段**：只截尾部、显式标注"已截断 N 条"，并说明如何去取全量。**永远不截中间**——中间截断会让数据看起来完整但实际错位，是最危险的失败模式。

（3）防御性设计（避免反复踩同一个坑）：
- 工具输出设硬上限（字节数/token 数），超限由工具自己降级返回摘要；
- 检测到"结果超限 → 截断 → 模型要求更多 → 再截断"的循环时，直接中断并告知模型"数据量超出上下文，请改用筛选条件或分批处理"，防止无限重试烧钱；
- 在 System Prompt 里明确告知模型"大结果以引用形式给出，需要细节请调用取回工具"，让模型的行为和这个机制匹配。

## 7. 什么时候结束 ReAct 循环

**【核心结论】**
ReAct 循环必须有**显式的终止条件集合**，包括正常终止和**至少五类异常终止**；异常终止也要输出结论，不能只抛异常。

**【展开回答】**

（1）正常终止：
- 模型返回**不含工具调用**的最终答案；
- 或者达到任务完成判定（验收条件满足）。

（2）五类必须实现的异常/兜底终止（这是面试的加分点）：

| 类型 | 判据 | 处理 |
|---|---|---|
| 步数超限 | `step >= max_steps` | 输出当前最好结果 + 说明未完成原因 |
| 无进展检测 | 相同工具 + 相同参数重复调用；观测结果无变化；计划不推进 | 中断，回退到重规划或直接回答 |
| 失败熔断 | 同一工具连续失败/超时 N 次 | 禁用该工具，改路径或降级 |
| 预算超限 | token / 费用 / 墙钟时间预算耗尽 | 中断并交回中间结果 |
| 用户取消 | 用户主动终止 | 立即停止调度，保存中间结果 |

（3）终止时的**正确交付方式**：
- 返回**已经取得的最佳结果**，而不是空手报错；
- 明确说明"为什么停"（哪条终止条件触发）；
- 明确说明"还缺什么"（哪些信息没拿到、哪些步骤没做完）；
- 标记这一轮为部分完成，支持用户补充约束后**继续**（而不是从头再来）。

（4）设计要点：
- 终止判定要放在**主循环里集中判断**，不要散落在各个工具实现里；
- 无进展检测需要维护一个"调用指纹集合"（工具名 + 归一化参数哈希）和一个"观测哈希"，两者都不变才算无进展；
- 任何终止路径都要走同一套收尾逻辑（落存储、释放资源、发事件），避免出现"有的终止保存了状态、有的没保存"。

## 8. 工具调用超时了，Agent 会卡死吗

**【核心结论】**
**取决于设计而不是取决于工具**。正确建模下，超时是**状态机里的一个正常状态**（`timed_out`），不是异常，Agent 一定不会卡死。

**【展开回答】**

（1）时间预算必须**分层设置**，一层比一层宽：
- 连接超时 < 读超时 < 工具级总超时 < 单步（step）看门狗 < 用户可感知的响应时限；
- 任何一层到期都必须**有确定的返回值**，不允许出现"无限等待"的代码路径。

（2）不卡死的六个机制：
1. **异步非阻塞**：工具调用是异步任务，主循环 await 的是有超时的 Future/Promise，不是无超时的阻塞 IO；并行工具调用设最大并发上限；
2. **取消传播**：取消信号（CancellationToken / AbortSignal）要能一路传到底层网络请求、子进程、数据库连接，超时那一刻就地释放资源；
3. **看门狗**：Agent 级的 watchdog 独立于业务超时，超时后强制让当前 step 返回 `timed_out` 并推进循环；
4. **结构化错误返回**：超时返回统一格式的错误对象（含耗时、是否可能已生效），而不是空值或抛异常穿透；
5. **幂等性判定**：区分"请求未发出"（可安全重试）和"已发出但无响应"（**结果未知**），后者必须记录为待核对，不能盲目重试；
6. **循环必须能推进**：超时后要么重试（有限次）、要么换工具、要么跳过并向模型报告，**永远不能原地等待**。

（3）最容易被忽略的一点：超时大多是**读超时**（请求已发出），语义上是**结果未知**而不是**确定失败**。所以"超时后重试"在写操作上是危险的——这属于第 12 题的内容，这里要主动点出来，体现你对语义的理解深度。

（4）兜底：即使某个工具实现有 bug 卡住了，看门狗 + 进程隔离（把工具跑在独立进程/线程里，可强杀）保证 Agent 主流程不受影响。

## 9. 工具调用超时卡死，模型不响应，用户取消触发，agent 应该怎么处理

**【核心结论】**
按优先级处理：**先停止调度新步骤，再处理在途调用与状态保存，最后把"未知的写操作"交给对账队列**。用户取消是一次**有序停机**，不是简单中断。

**【展开回答】**

（1）用户取消触发时，Agent 的动作序列：

1. **停止调度**：立刻停止规划新 step、停止发起新工具调用（这是最优先的，防止取消过程中又产生新的副作用）；
2. **传播取消信号**：向所有在途工具调用发送取消，等待一个**短的宽限期**（比如几百毫秒到几秒）让它们返回；能干净退出的就标记 `cancelled`；
3. **处理"结果未知"的在途写操作**：宽限期内没返回的、尤其是写操作，**不能假设它失败**。把它们记入 **pending/不确定队列**（含 idempotency key、参数、发起时间），由后台核对任务去查询或补偿。这是取消场景里最关键的工程细节；
4. **进程与资源回收**：强杀工具子进程/进程组，释放文件锁、数据库连接、分布式锁、临时资源；
5. **状态持久化**：把这一轮标记为 `cancelled`，保存已完成步骤、部分结果、当前计划的进度点，并保留足够信息支持**续跑**；
6. **响应与收尾**：向用户明确回报——已完成了什么、哪些被取消、哪些写操作结果待确认、后续如何恢复；对已经产生副作用的写操作生成审计记录，避免"用户以为没做、其实做了"。

（2）"模型不响应"要单独处理（这和工具超时是两件事）：
- 模型侧也有超时 + 重试：区分**首 token 前挂起**（可安全重试，因为请求可能未开始生成）和**流式输出中断**（部分内容可能已产生，要谨慎）；
- 有备用模型/供应商时做 failover（换模型、换 region）；
- 上下文过大导致模型挂起时，先压缩上下文再用更小的 prompt 重试；
- 重试耗尽后**降级**：返回已有的最好结果并说明原因，或进入安全模式（只允许读操作，禁止新的写操作）。

（3）一句话总结我的处理哲学：**取消 = 停止新增副作用 + 妥善处理不确定的存量副作用 + 可恢复的状态保存**。核心难点从来不是"停下来"，而是"停下来之后，那些发出去但没回来的写操作怎么收尾"。

**【追问预判】**
- "如果用户取消时工具刚好写成功了但还没返回？" → 正是上面第 3 点，靠 idempotency key 去查询/补偿，不能靠猜。

## 10. 卡死的工具怎么处理

**【核心结论】**
卡死要**从机制上让它可杀、可隔离、可异步化**；杀不掉的就**转为异步任务 + 僵尸任务列表**，靠外部核对收尾。

**【展开回答】**

（1）先做机制建设（治本）：
- **网络层短超时**：底层 HTTP/DB 客户端设短连接与读超时，让"卡"在最早的一层被掐断；
- **进程隔离**：工具跑在独立进程/线程/容器里，可被强杀，卡死不影响 Agent 主进程；
- **异步化长任务**：正常耗时长的工具不阻塞循环，改为**提交任务拿 handle**，之后轮询或等通知；这样"长"和"卡"就被区分开了；
- **可恢复设计**：工具支持幂等 + 检查点（checkpoint），重试时从断点续跑，而不是从头再来。

（2）真的卡死时的处理策略（按顺序）：

| 情况 | 处理 |
|---|---|
| 偶尔超时 | 有限次重试（指数退避 + 抖动），失败则上报模型换路径 |
| 反复超时 | 该工具进入**熔断/隔离名单**，一段时间内不再调用，并向模型说明"此工具暂不可用，请换方案" |
| 无法杀死（如第三方 API 卡住） | 转成**异步任务**，记入"僵尸/悬挂任务列表"，带着业务幂等键后台核对；Agent 继续做别的或结束这一轮 |
| 调用代价高但可续 | 记录检查点，稍后从断点恢复 |

（3）**对账（reconciliation）是收尾的关键**：
清理动作不可靠，所以不能只依赖"杀干净"。所有"发起过但结果未知"的操作都要进对账队列，由定时任务去查询真实状态、决定补偿还是确认成功。这是把不确定性收敛掉的唯一稳妥办法。

（4）**熔断与健康检查**：连续超时/失败的工具有明确阈值（如 3 次），熔断后定期做健康探测，恢复后才放回可用列表；同时这类事件要计入监控指标（工具超时率、熔断次数），作为可观测性的一部分。

（5）要避免的反模式：无超时地 await、超时后不取消底层请求（线程/连接泄漏）、无限重试、把"结果未知"当"失败"直接重试写操作。

## 11. 如果卡死的工具是脚本怎么办

**【核心结论】**
脚本是**最危险的一类工具**（可能死循环、交互阻塞、吃满资源），处理方式是**沙箱化 + 资源限额 + 进程组强制终止 + 禁止交互 + 版本冻结**。

**【展开回答】**

（1）风险清单（先说清楚风险，再讲方案）：
- 死循环 / 自己 fork 出一堆子进程；
- 等待 stdin（没人会输入）而永久阻塞；
- 加载或输出超大数据，把内存和上下文都撑爆；
- 脚本内容每次由模型动态生成 → 不可复现、不可审计、无法回滚。

（2）执行侧限额（必须全部设上）：
- **墙钟超时**（wall-clock）+ 到期强制终止；
- **资源限制**：CPU 时间、内存上限、进程数/线程数、打开文件数（容器里用 cgroup / `ulimit`，进程内用受限执行环境）；
- **输出限额**：stdout/stderr 设字节上限，超限即截断或直接掐断，避免日志把上下文冲爆（只保留末尾 N 行，便于看报错）；
- **网络与文件系统**：默认最小权限（要么禁止出网，要么走白名单代理；只挂载必要目录）。

（3）终止方式（要能杀干净）：
- 脚本在**独立进程组 / Job Object** 里跑，终止时杀整个进程组，避免**孤儿进程**残留；
- 先发温和终止信号，宽限期后再强杀；
- 杀完校验进程确实退出，并释放临时文件与句柄。

（4）交互与输入：
- 脚本必须**参数化、非交互**；检测到脚本在读 stdin 就视为失败并终止（不能等）；
- 禁止脚本里出现"等用户确认"的逻辑，需要确认的走 Agent 的审批流程。

（5）脚本来源与治理：
- **脚本版本冻结**：只允许执行**预先审核注册**的脚本（带版本号），禁止模型临场生成任意代码执行；如果一定要生成，必须走静态检查 + 沙箱 + 人工审核队列；
- **幂等**：脚本设计成可重复执行（比如用幂等键或先查后写），超时重试才安全；
- 每次执行记录：脚本 id/版本、参数、退出码、耗时、输出摘要，保证可审计、可回放。

（6）超时后的处理：计入熔断计数、进入待对账队列（脚本可能已部分生效）、必要时从中间断点续跑。

一句话：**对脚本工具的信任级别应该最低——默认它不可信，所有约束（时间、资源、IO、网络）都在外部强制，绝不靠脚本自己"守规矩"。**

## 12. 工具出现网络异常怎么办，如果有写操作怎么处理

**【核心结论】**
先**给错误分类**，核心是区分三种语义状态：**确定未发出（可重试）/ 确定失败（可重试）/ 结果未知（不能重试，必须先核对）**。读操作可重试，**写操作必须以幂等为前提**。

**【展开回答】**

（1）错误分类（这一步决定了后面所有动作）：

| 错误类型 | 语义 | 处理 |
|---|---|---|
| DNS 失败、连接被拒、连接超时 | 请求**未送达** | 可安全重试（退避 + 抖动） |
| 429 / 限流 | 未处理 | 退避重试，并配合令牌桶限流 |
| 5xx / 服务端错误 | 大概率未生效（不绝对） | 有限重试 |
| 4xx 参数/权限错误 | 重试无用 | 立即失败，返回模型改参数或换方案 |
| **读超时 / 连接中断且已发出** | **结果未知** | **不盲目重试**，先查询确认状态 |

（2）读操作：标准重试策略——指数退避 + 随机抖动、设置最大重试次数与总时间预算、必要时切换备用端点/备用供应商；重试次数和耗时全部埋点。

（3）写操作（重点，面试官就想听这段）：
- **幂等键（idempotency key）是硬要求**：由"业务操作 + 参数"确定性地生成（不要用随机数，否则重试会变成新操作）；下游服务侧对同一 key 去重，保证重放安全；
- **优先改成天然幂等**：比如"设置为目标状态"（set 语义）而不是"增量修改"（increment 语义）；
- **乐观并发控制**：带版本号/ETag，避免覆盖别人的修改；
- **重试前先查**：先调查询接口确认上一次是否已生效，再决定重试/跳过；
- **结果未知的处理**：写入待核对队列，由定时对账任务去查询真实状态并补执行或标记成功；不确定状态**必须落到存储里**，不能只存在于内存；
- **权限降级**：在异常/不确定状态下，Agent 应停止新的写操作，退化为只读模式。

（4）整体防线（把单点处理升级成体系）：
1. 分类与语义判定（上面这张表）；
2. 退避重试 + 抖动 + 限流；
3. 幂等键 + 去重；
4. 熔断器（连续失败打开熔断，避免打爆下游）+ 降级（排队延后、只读、转人工）；
5. 对账/补偿任务；
6. 全链路审计：**写操作"尝试过"就必须留痕**，包括失败和未知状态的尝试，否则事后无法判断是否产生过副作用。

（5）一句话总结：**网络异常本身是常态，风险不在"失败"，而在"不确定"。所有的工程投入都围绕一件事——把"不确定"转成"确定可核对"的状态。**

# 二、设计题

## 题目：广告 Agent 支持用户表达"创建定时任务，扫描近 7 天无消耗计划并暂停"，怎么设计实现

**【核心结论】**
把自然语言需求**编译成一份声明式的任务 DSL**，再把这份 DSL 交给**确定性的执行状态机**去跑。模型只出现在"解析意图"和"生成解释"两个端点，**判定和写操作全部是确定性代码**。

**【展开回答】**

（1）整体链路（五段式）：

```
用户自然语言
   → ① 意图解析（LLM）→ 任务 DSL
   → ② 校验与确认（Schema 校验 + 语义校验 + dry-run 影响面 + 用户确认）
   → ③ 落库（任务定义 + 版本 + 审计）
   → ④ 调度触发（cron 引擎 + 分布式锁 + 幂等执行 id）
   → ⑤ 确定性执行 DAG（查询 → 判定 → 生成动作草案 → 风控/审批 → 写操作 → 审计/通知）
```

（2）关键设计决策：

| 决策 | 选择 | 理由 |
|---|---|---|
| 用什么表达需求 | **声明式 DSL**（结构化 JSON/YAML） | 可校验、可版本化、可 diff、可审计、可回放 |
| 执行引擎 | **确定性工作流/状态机（DAG）**，不是 ReAct 自由循环 | 无人值守必须可预测、可测试、可回滚 |
| 模型参与范围 | 只在①解析 + ⑤生成解释；异常时参与路由 | 判定必须是可复现的规则，不能是概率事件 |
| 动作接口 | 幂等键 + 限流 + 审批 | 广告投放是真实资金操作，必须可撤回 |
| 判定与执行分离 | **先产出动作草案（dry-run），再执行** | 让影响面可见，给审批和回滚留出空间 |

（3）数据模型（DSL 大致长什么样）：

```yaml
task:
  id: t_001
  name: "近7天无消耗计划暂停"
  trigger:
    type: cron
    expr: "0 30 3 * * ?"        # 每天 03:30，低峰期
    timezone: "Asia/Shanghai"
  scope:
    entity: campaign
    metric: { name: cost, source: unified_daily, field: spend }
    window: { type: relative, days: 7, offset: -1 }   # T-1 往前推 7 天，避开数据延迟
    condition: { spend: 0 }                            # 可选：impressions == 0 且 age_days > 7
  action:
    type: pause
    params: {}
  governance:
    approval: { mode: auto_below: 50, manual_above: 50 }  # 超过 50 个走人工审批
    idempotency_key: "${task_id}:${run_id}:${campaign_id}"
    retry: { max: 3, backoff: exponential }
    rollback: { type: snapshot_restore }
    dry_run: true
  notify: { channels: [im, email], on: [success, failure, needs_approval] }
```

（4）执行流程（确定性步骤，每步都有幂等和留痕）：
1. 取分布式锁 + 生成 `run_id`，建立这一次执行的上下文；
2. **查询候选**：用统一指标口径拉近 7 天消耗，筛出 `spend == 0` 的计划（在数据层做，不拉全量到内存）；
3. **排除与校验**：排除新建未起量、投放期已结束、已被人工锁定、非本任务范围的计划；再调广告 API 校验实时状态与可操作性；
4. **生成动作草案 + 快照**：每条动作记录 `{campaign_id, 判定依据, 当时的指标快照, 预期结果}`；
5. **风控与审批**：动作数量/影响的预算规模超阈值 → 转人工审批（审批通过再继续）；
6. **执行写操作**：分批 + 限流 + 幂等键；按 plan 粒度记录成功/失败/未知；
7. **审计与通知**：写审计日志（谁触发、依据是什么、做了什么、结果如何），发通知，失败项进重试/对账队列。

（5）必须点出的工程细节：
- **口径与时间窗口**：7 天要明确是自然日还是滚动窗口、用 T-1 汇总还是实时数据、数据延迟怎么兜（先看汇总表，缺口用实时表补）；否则同一天跑两次结果都不一样；
- **幂等**：同一次 run 重跑不能重复动作（run_id + plan_id 做幂等键）；
- **补偿/回滚**：暂停前保存原状态快照，支持批量恢复；恢复动作因为涉及重新花钱，要有额外授权；
- **超时与网络异常**：读可重试，写必须幂等；结果未知进对账队列；
- **可观测性**：命中数、动作数、成功率、跳过原因分布、任务耗时全部埋点。

（6）一句话收尾：**这道题的关键不是"让 Agent 更聪明"，而是把"聪明"限制在解析需求那一小步，其余全用确定性的、可审计、可回滚的工程机制兜住。**

---

## 追问题 1：定时任务包含什么

**【核心结论】**
一个可运维的定时任务 = **触发 + 范围（查什么）+ 判定（怎么算）+ 动作（做什么）+ 治理（怎么保证安全）+ 通知 + 可观测**。

**【展开回答】**

（1）基本信息：任务 id、名称、描述、创建者、**原始自然语言需求**（保留原文便于追溯）、DSL 版本号、创建/修改时间。

（2）触发（Trigger）：
- cron 表达式 / 固定间隔 / 一次性；
- **时区**（必须显式指定，否则跨时区出错）；
- 生效时段与有效期（start/end）、错过的策略（misfire：补跑 or 跳过）；
- 并发控制：是否允许重入、分布式锁 key、上次执行未结束时本次如何处理。

（3）范围（Scope / 查询定义）——最容易被忽略但最关键：
- 实体维度（账户/计划/单元/创意）；
- 指标口径（消耗、曝光、点击、转化）与**数据源表**（汇总/实时）；
- 时间窗口（相对窗口 + offset，避数据延迟）与**时区**；
- 过滤条件（状态、账户白/黑名单）；
- 数据延迟容忍与补数策略。

（4）判定（Condition）：
- 判定表达式（阈值、连续 N 天、组合条件）；
- **边界与排除规则**（新建未起量、投放期结束、人工锁定）；
- 判定所需的最小样本（例如需要至少 N 天数据才判定，避免误杀）。

（5）动作（Action）：
- 动作类型（暂停、预算调整、出价调整、通知人工）；
- 参数与作用粒度；
- 动作前置检查、后置校验；
- 动作的**可逆性**描述与回滚方式。

（6）治理（Governance）——保证"不会闯祸"的部分：
- 审批策略（自动/人工阈值）、审批人与超时策略；
- 幂等键规则、重试策略、超时、熔断；
- 执行窗口（低峰期）、限流、单次动作数量上限；
- dry-run 开关、灰度/白名单、止损阈值；
- 失败策略（跳过/告警/中止整批）。

（7）通知与告警：通知渠道、触发事件（成功/失败/需审批/命中数异常）、告警阈值与收敛（避免消息风暴）。

（8）可观测与审计：执行记录（run 表：开始/结束/命中数/动作数/状态）、动作明细（action 表：判定依据 + 快照 + 结果）、指标埋点、日志与链路追踪。

（9）权限与合规：谁有权创建/修改/停用任务；操作留痕；敏感动作的授权范围。

一句话：**定时任务不是"一个 cron + 一段脚本"，而是一个带治理能力的小型作业系统。**

## 追问题 2：定时任务执行，需要模型参与吗

**【核心结论】**
**拉取和判定完全不需要模型参与（而且不应该参与）**。模型只在解析需求、生成解释、异常路由这三处出现。

**【展开回答】**

（1）为什么判定不能用模型：
- **不可复现**：同样的输入可能给出不同结果，而"无消耗就暂停"是明确的规则；
- **不可验证**：规则用 SQL/代码表达可以单元测试、可以做并行校验；模型的输出只能靠抽查；
- **性能与成本**：每天扫全量账户，模型既慢又贵，而数据层一条聚合查询就能完成；
- **合规与审计**：广告投放涉及真实资金，判定依据必须能被逐条解释和追责；
- **幻觉风险**：模型可能编造不存在的计划 id、算错阈值、漏掉边界条件。

（2）模型**应该**参与的三处：
1. **入口**：把"帮我盯着那些跑了一周没花钱的计划，没量的就停掉"翻译成 DSL（含字段映射、阈值推断、时间窗口理解），并把 DSL **反述给用户确认**；
2. **出口**：把执行结果生成人类可读的报告与解释（"本次命中的 37 个计划自 X 日起连续 7 天消耗为 0，已暂停，详情见附表"）；
3. **异常/兜底**：遇到未预期错误（未知错误码、口径异常、大面积失败）时做**路由建议**——是重试、降级、还是转人工；这类"泛化判断"是模型的强项，但**只给建议不直接执行**。

（3）结构上的结论：链路应该是 **"确定性工作流做主干，模型做入口解析和出口解释"**，而不是 ReAct 自由循环。这也是为什么我倾向于把这类需求实现成"NL → DSL → 工作流"，而不是"NL → Agent 自己调工具跑"。

（4）补充一个边界：如果需求本身是**开放的、需要多轮探索**的（比如"帮我把 ROI 提上去"），那才需要 Agent 去做规划；而"扫近 7 天无消耗计划并暂停"是**封闭的、可枚举的**，就应该固化成工作流——**用 Agent 的地方要克制，能用工作流就不用 Agent**。

## 追问题 3：怎么保证模型写出来的正确性

**【核心结论】**
核心思路是**把模型从"执行者"降级为"受限的翻译器"**，然后用 **Schema 校验 → 语义校验 → dry-run 预演 → 影响面确认 → 分级执行** 五道闸门把它框住，再加上回归测试和可回滚作为长期保障。

**【展开回答】**

（1）约束输出形态（第一道闸门）：
- 强结构化输出（JSON Schema / Function Calling / Pydantic 校验），**不合法就重试**并记录样本；
- 用枚举/白名单限定可选字段和取值，**不允许自由写 SQL、自由写脚本、自由拼 URL**；如果必须放开查询能力，也只在受限模板 + 只读账号 + 强制 LIMIT 下做；
- Few-shot 只给正例和典型边界例，降低格式漂移。

（2）语义校验（第二道闸门，光有 Schema 不够）：
- **ID 真实性**：模型给出的计划/账户 id 必须在下游真实存在且属于当前用户（防幻觉 + 防越权）；
- **条件合理性**：阈值是否在域内、时间窗口是否合法、动作组合是否冲突；
- **动作白名单**：只允许声明式枚举动作（pause / set_budget），任何不在白名单的一律拒绝；
- **授权范围**：任务只能作用在用户有权限的实体上。

（3）预演与确认（第三道闸门，最关键的一步）：
- 真实数据 **dry-run**：先只判定不执行，产出"将影响 X 个计划、涉及日消耗 Y 元"的**影响面报告** + 抽样明细；
- 让用户/审核人**确认后再落库执行**；批量或不可逆动作走审批流；
- 这一步的价值在于把"模型的错"暴露在**没有副作用**的阶段。

（4）执行的规模护栏（第四道闸门）：
- 单次动作数量上限、分批执行、限流、低峰期执行；
- 幂等键，防止重试导致重复动作；
- 不确定状态（超时/网络异常）进对账队列，不盲目重试。

（5）可逆性与止损（第五道闸门）：
- 动作前保存快照，支持**一键回滚/批量恢复**；
- 设定止损阈值（例如命中数超过历史均值 N 倍就自动暂停任务并告警），异常规模自动熔断而不是继续执行。

（6）长期保障机制（回答深度加分项）：
- **黄金回归集**：几百条人工标注的"需求 → DSL"样本 + 线上 bad case 固定成回归集，任何 prompt / 模型 / 工具变更都要全量跑，指标是解析准确率与危险字段错误率（危险字段错误必须是 0）；
- **影子模式（shadow）**：新任务先在生产只判定不执行，产出日报，与人工判定对比，差异分析通过后再放开；
- **小流量灰度**：单账户 → 小流量 → 全量，每步都有止损阈值和回滚预案；
- **模型与 Prompt 版本化**：审计日志记录模型版本 + prompt 版本，保证任意一次执行都能复现当时的决策依据；
- **可观测指标闭环**：解析成功率、人工修改率（改得越多说明模型越差）、Schema 校验失败率、误 pause 率、漏 pause 率、执行成功率、回滚次数——用这些指标持续优化而不是靠感觉；
- **人机兜底**：关键动作保留人工确认入口，重大动作双人复核，避免全自动化下的一次性大事故。

（7）一句话总结：**保证模型正确性的本质，是不给它"直接造成不可逆后果"的机会——用验证、预演、审批、可回滚这四件事，把概率性的生成环节包在确定性的执行骨架里。**
